# Upgrading to 2.2.0

Version 2.2.0 adds optional response simulation and stronger test isolation.
Legacy results, existing factory calls, and documented CommonJS/ESM imports remain
supported. Nodemailer 6–10 remain in the peer range.

## Install

```sh
npm install --save-dev nodemailer-mock@^2.2.0
```

Keep the application's Nodemailer dependency. For TypeScript on a Nodemailer
version without bundled declarations, use compatible `@types/nodemailer` types.

## Existing behavior

`getMockFor(nodemailer)` and the shared default mock still return legacy
`MockSentMessageInfo` results, including the string envelope. `reset()` retains
transporters, plugins, individual close counts, and current idle state.

Default failure `Error` objects now belong to one mock instance and one reset
period. Compare against that instance's `mock.getFailResponse()` when asserting
identity. Custom errors supplied through `setFailResponse()` or `queueResult()`
retain their identity until reset clears the setting.

A send started before reset still settles for its original caller, but its
completion cannot populate the new sent-mail history. This applies when compile
or stream plugins finish asynchronously. Await sends when their result matters;
reset is a history boundary, not cancellation of their returned Promises.

Use `mock.reset({ clearTransporters: true })` for explicit cleanup. It also
clears the registry, removes retained transporter listeners, and resets their
idle states and individual close counts. It does not close real transports.
Held transporter references remain usable, but the registry no longer tracks
them and their prior listeners have been removed.

## Optional response simulation

Pass `{ responseMode: 'realistic' }` as the second argument to `getMockFor()`.
TypeScript then infers `RealisticMockSentMessageInfo`: its envelope contains
`from` and `to`, accepted recipients derive from the compiled envelope, rejected
and pending default to empty arrays, and the compiled message ID is returned.
An optional `messageIdGenerator` overrides IDs for deterministic tests.

`mock.setSentMessageInfo(info)` configures typed partial results for successful
sends. `mock.queueResult({ error })` queues a failure;
`mock.queueResult({ info })` or `mock.queueResult({})` queues a success. Sends
reserve outcomes in invocation order, even when plugins finish out of order.
Queued outcomes override failure flags/checks for that send, do not consume a
one-time failure flag, and are not consumed by `verify()`. Queued result fields
override persistent result fields.

Reset clears both result overrides and the send queue while retaining the
factory response mode and factory ID generator. These results simulate transport
behavior; no real delivery occurs.

## Compatibility and dependency checks

The ESM wrapper now exports both default and named APIs with matching
declarations. It preserves the shared CommonJS singleton. Custom transports with
nonstandard result types are accepted by the TypeScript API; mock send results
continue to use the configured mock result type.

CI tests packaged consumers on Node.js 22 and 24 with exact Nodemailer baselines
6.10.1, 7.0.13, 8.0.11, 9.1.1, and 10.0.9. The locked development version receives
its own quality, coverage, examples, and package checks. See the
[release runplan](../RELEASING.md) for reproducible commands.

This release also refreshes compatible development dependencies and removes the
cleanup utility dependency in favor of Node.js file removal. Refer to the
[changelog](../../CHANGELOG.md) for the shipped changes.

  realistic results and the required realistic-mode discriminator.

- README JavaScript syntax, documentation relative links, archive contents, and
  Git whitespace checks.

The archive contains only package metadata, license, README, changelog, compiled
JavaScript and declarations. No source, test tooling, local reports or release
credentials are included.

eligible ts-jest 29.4.14 while 29.4.15 is younger than the configured release-age
policy. Existing glob deprecation and Node experimental-test diagnostics are
separate from the clean security audits. Remote CI and registry publication are
verified separately by the release workflow and registry readback.
